1.한눈에 보기

Nikon Value는 eBay 매물 기반 니콘 중고 시세 트래커입니다. GitHub Actions가 3시간마다 시세를 수집해 정적 사이트를 재생성하고(GitHub Pages 배포), 별도의 FastAPI 서버(라즈베리파이)가 소셜 로그인과 관심 목록을 담당하는 이원 구조입니다. 종합 평가는 B− 입니다. 운영 자동화·데이터 정제 로직·백엔드 보안 기본기는 개인 프로젝트 수준을 훌쩍 넘지만, ① 빌드 산출물이 소스 저장소에 섞여 커밋되는 구조, ② 1,000줄이 넘는 모놀리식 스크립트 2개, ③ 파이프라인·프론트엔드 테스트 부재, ④ 인증 토큰 취급 방식이 다음 단계 성장을 막는 4대 부채입니다.

아키텍처 설계정적 사이트 + 자동 파이프라인 + 보조 API 분리는 비용·안정성 면에서 탁월. API 다운 시에도 시세 조회가 동작하는 graceful degradation.
B
데이터 파이프라인규칙 → LLM → IQR 3중 필터, 적응형 가격 상한, 환율 3단계 폴백 등 정제 로직이 영리함. 다만 모놀리식이고 테스트가 없음.
B
백엔드 API전 쿼리 파라미터화, HMAC state, rate limit, async 일관성. JWT 시크릿 무검증과 토큰 전달 방식이 감점 요인.
C+
프론트엔드무프레임워크 경량 접근 자체는 적절. escapeHtml 3중 정의, admin 인라인 JS 627줄, 전역 상태, 하드코딩 URL이 문제.
C
테스트서버 38개는 잘 짜였으나 fetch/build 파이프라인(2,700줄)과 JS(1,600줄)는 사실상 0%. CI에서 테스트를 돌리지 않음.
C+
보안SQL 인젝션·CSRF 방어, admin 3중 잠금은 양호. JWT 시크릿 빈 값 허용, localStorage 토큰, fail-open 검증이 약점.
C+
운영 / CI3시간 자동 수집 + 실패 시 이슈 자동 생성은 모범적. 그러나 테스트 CI 부재, 충돌 시 데이터 유실 가능한 push 로직.
B−
문서화README·HISTORY가 실제와 일치하고 충실. 아키텍처 다이어그램, 서버 배포·운영 문서는 없음.

4.잘 만들어진 부분

리팩토링 시 깨뜨리지 말아야 할 자산이기도 합니다.

4.1 데이터 정제 — 이 프로젝트의 핵심 경쟁력

  • 우수 3중 필터 파이프라인: 38개 제외 패턴 + 렌즈 후드 정규식 + 수동렌즈 세대(AI/AI-S/Series E) 충돌 감지(규칙) → LLM 타이틀 분류 → IQR 아웃라이어 제거. 특히 LLM이 전부 걸러내면 휴리스틱 결과를 유지하는 폴백(fetch_prices.py:301-306)은 LLM 오판에 대한 좋은 방어.
  • 우수 적응형 가격 탐색(fetch_prices.py:557-636): 검색 결과가 상한에 붙어 있으면(98% 트리거) 상한을 1.5×/2.0×로 넓혀 재검색 — 시세 급등 제품을 놓치지 않는 장치.
  • 우수 환율 3단계 폴백: ECB 실패 → 기존 catalog.json 값 유지 → 최근 daily 스냅샷에서 복구(fetch_prices.py:823-836).

4.2 백엔드 기본기

  • 모든 SQL이 파라미터화되어 있고(인젝션 불가), FK CASCADE + WAL 모드 활성화(server/database.py).
  • OAuth state를 HMAC-SHA256 서명 + 5분 만료로 처리(server/auth/oauth.py) — CSRF·리플레이 방어.
  • rate limit(인증 5/min, API 60/min), CORS 단일 오리진 화이트리스트, 관심목록은 카탈로그 ID 대조 검증.
  • admin 서버는 local-only + 세션 토큰 + same-origin 3중 확인(admin_server.py:42-91).

4.3 운영·SEO·UX 디테일

  • 수집 실패 시 GitHub 이슈 자동 생성, 데이터가 2일 이상 오래되면 사이트에 stale 배너 노출.
  • JSON-LD(Product/AggregateOffer), canonical, OG 태그, sitemap 331건, <noscript> 히스토리 테이블까지 — 정적 사이트 SEO 모범.
  • WebP srcset, skeleton UI, aria 레이블, 통화 토글(USD/KRW)의 null-safe 처리.

5.핵심 문제점 (우선순위별)

모든 항목은 실제 코드를 열어 검증했습니다. P0 보안·데이터 무결성 / P1 구조 부채 / P2 개선 권장.

P0 — 즉시 조치

문제위치내용과 영향
P0-1 CI에서 테스트를 안 돌린다 .github/workflows/ 워크플로는 update-prices.yml 하나뿐. 잘 짜인 테스트 38개가 로컬에서만 의미를 가짐. 리팩토링을 시작하면 회귀를 잡아줄 안전망이 0이므로 모든 작업 중 1순위.
P0-2 JWT 시크릿 무검증 server/config.py:16 JWT_SECRET_KEY = _env("JWT_SECRET_KEY") — .env 누락 시 빈 문자열로 서버가 그대로 기동하고, 모든 토큰이 빈 키로 서명됨(누구나 위조 가능). 시작 시 길이 검증 1줄이면 차단됨.
P0-3 토큰 전달·보관 방식 server/auth/routes.py · js/auth.js:8-10 JWT가 URL fragment(#token=…)로 전달되고 localStorage에 7일간 보관. XSS 발생 시 토큰 탈취로 직결. 현재 외부 스크립트가 GA·Chart.js뿐이라 실위험은 중간이지만, 기능이 늘수록 위험이 커지는 구조.
P0-4 충돌 시 조용한 데이터 유실 update-prices.yml:50 git push || (git pull --rebase -X ours && git push) || echo "Push skipped…" — rebase에서 -X ours는 충돌 시 원격을 우선하므로 방금 수집한 데이터가 버려질 수 있고, 마지막 || echo가 실패를 삼켜 워크플로는 성공으로 표시됨. 실패 이슈 생성 스텝도 발동하지 않음.

P1 — 구조 부채 (리팩토링 본체)

문제위치내용과 영향
P1-1 빌드 산출물이 소스 저장소에 커밋 루트 index.html, products/ 331장, sitemap.xml … 3시간마다 산출물 커밋 → 최근 커밋 50개 중 48개가 자동 데이터 커밋. 사람의 변경이 묻히고, diff 리뷰가 불가능하며, 저장소가 계속 비대해짐(.git 12MB+). 소스/산출물 분리가 모든 구조 개선의 전제.
P1-2 모놀리식 스크립트 2개 fetch_prices.py(1,073) · build_static_site.py(1,324) fetch는 API 클라이언트·필터·통계·저장이, build는 데이터 머지·HTML 템플릿·파일 배치가 한 파일. HTML을 f-string으로 조립해 수동 escape가 41곳 — 템플릿 엔진(Jinja2)이 정확히 해결하는 문제. head_block/head_block_product는 CSS 경로만 다른 복붙(build:391-428).
P1-3 프론트 코드 3원화 site.js · auth.js · admin.html 인라인 627줄 escapeHtml이 3곳에 각각 정의(site.js:111, auth.js:223, admin.html:887). admin은 모듈화·반응형·공용 스타일 전부 단절. 전역 window.nikonValueAuth/Catalog로 스크립트 간 암묵 결합.
P1-4 하드코딩 산재 여러 파일 API 서버 주소(auth.js:4), GA 측정 ID(build:33), 필름 보드 핫스팟 좌표 84줄(build:52-135), eBay 카테고리 매직값 {"31388","3323"}(fetch:374), 어필리에이트 헤더가 placeholder 그대로 전송 중(fetch:455 — <ePNCampaignId>).
P1-5 파이프라인 테스트 공백 tests/ 핵심 수익 로직인 compute_stats(IQR), 적응형 가격 탐색, merge_catalog_with_config, 가격 변화 계산이 모두 미커버. 빌드 결과물 골든 테스트도 없어 build 스크립트 수정이 곧 도박. JS 테스트 0건.

문제위치내용

7.추가 기능 제언

기준: 이미 가진 자산(3시간 파이프라인 · 로그인+관심목록 · 시계열 데이터)과의 시너지가 큰 것부터. 효과/난이도는 상대 평가입니다.

기능효과난이도설명
⭐A. 딜 레이더높음낮음수집 시 이미 매물별 가격을 보유. "중앙값 대비 −20% 이하" 매물에 뱃지 + 홈에 '오늘의 딜' 섹션. 기존 rare-watch 인프라 재활용으로 며칠 안에 가능. 사이트의 핵심 가치("싸게 사기")에 직결.
⭐B. 가격 하락 알림높음중간관심목록 제품이 설정가 이하로 내려가면 이메일 알림. 로그인+관심목록+주기 파이프라인이 전부 준비되어 있어 시너지 최대 — 파이프라인 끝에 알림 잡 추가 + 서버에 알림 설정 API. 재방문을 만드는 기능.
⭐C. 내 장비 가치 대시보드높음중간관심목록을 '보유 장비'로 확장해 합산 가치 추이 차트 제공("내 니콘들 오늘 시세"). 프로젝트의 출발점(mynikons.jpg)과 정체성이 일치하며 로그인 유인이 생김.
D. 통계 고도화중간낮음차트에 7일 이동평균 토글, '역대 최저가' 뱃지, 매물 수 추이 보조축. 데이터는 이미 다 있음.
E. 제품 비교중간중간2~4개 제품 히스토리 차트 오버레이 (Z6II vs Z7 등 구매 갈등 해소 페이지). URL 파라미터 기반이면 정적 구조 유지 가능.
F. 상태(컨디션)별 시세중간중간이미 LLM이 타이틀을 읽고 있으므로 등급(민트/양호/하자) 추출만 추가하면 "상태별 중앙값" 제공 가능 — 중고 시세의 실질 변별력 상승.
G. 월간 시세 리포트중간낮음Actions로 월 1회 '상승/하락 TOP 10' 페이지 자동 발행(+RSS). SEO·재방문에 기여.
H. 판매 체결가 추적높음높음현재는 호가 기반. eBay Marketplace Insights API(승인 필요)로 실제 체결가를 보완하면 데이터 신뢰도가 한 차원 상승. 승인 가능성 조사부터.
I. 일본 시장 소스높음높음클래식 니콘 물량의 중심은 일본(야후옥션 등). 소스 추가 시 가치가 크지만 API/크롤링 정책 검토와 필터 재설계가 필요 — Phase 3 이후 과제.
J. 작은 개선들낮음낮음다크모드, PWA(홈 화면 추가), 공개 데이터 API 문서화(catalog.json은 이미 공개 — 문서만 쓰면 됨), 영어판(i18n)은 수요 확인 후.
권장 순서 Phase 0~1 완료 → A 딜 레이더(빠른 성과) → B 가격 알림(Phase 3의 DuckDB와 연계) → C 장비 대시보드. H·I는 데이터 소스 확장이라 별도 트랙으로 사전 조사만 먼저.

8.바꾸지 말아야 할 것 — 과잉 리팩토링 경계

  • 무프레임워크 프론트엔드 유지: JS 총 1.6k줄 규모에 React/Vite 도입은 빌드 복잡도만 키움. 유틸 통합과 모듈 분리로 충분.
  • 정적 사이트 + GitHub Pages 유지: 무료·무장애·CDN 내장. SSR/호스팅 이전은 해결할 문제가 없음.
  • SQLite 유지: 현 트래픽에서 PostgreSQL 전환은 운영 부담만 증가. 백업 자동화가 먼저.
  • YAML 카탈로그 유지: 사람이 읽고 고치는 소스로 적합하며 admin UI와 백업 체계도 이미 있음.
  • requests 기반 동기 파이프라인 유지: 배치 작업에 async 전환은 복잡도 대비 이득 없음. eBay rate limit이 병목이지 동시성이 아님.
