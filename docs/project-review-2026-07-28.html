1.요약과 종합 등급

Nikon Value는 GitHub Actions가 3시간마다 eBay 매물을 수집해 331개 니콘 제품의 시세를 정적 사이트로 재생성하고, 별도 FastAPI 서버가 소셜 로그인·관심목록·가격 알림을 담당하는 이원 구조입니다. 직전 리뷰에서 지적된 P0 4건과 P1 5건 중 8건이 해소되어 구조 부채가 크게 줄었습니다. CI가 생겼고(ruff + pytest + JS 문법 + 빌드 스모크), 1,000줄 모놀리식 스크립트 2개는 13개 모듈로 분해됐으며, 골든 파일 테스트가 빌드 산출물을 바이트 단위로 고정하고 있습니다.

종합 등급은 B (직전 B−에서 상향)입니다. 감점 요인은 성격이 바뀌었습니다. 과거의 "구조가 무너져 있다"에서 "구조는 잡혔는데 운영 한계선에 닿아 있다"로 이동했습니다. 구체적으로 ① 배포 산출물에서 이미지 1개가 누락돼 3개 카테고리 탭의 히어로 이미지가 깨져 있고, ② eBay API 호출량이 일일 무료 한도(5,000)에 사실상 도달했으며, ③ 산출물·저장소에 7~8MB 규모의 순수 중복이 쌓이고 있고, ④ 가격 알림 기능이 발송 채널 부재로 완전히 비활성 상태입니다.

5.발견된 결함 (우선순위별)

5.1 P0 D-1 · 배포 산출물에 히어로 이미지 1개가 누락되어 렌즈 카테고리에서 이미지가 깨짐

위치nikon_value/sitegen/build.py:98-127 (copy_assets) ↔ nikon_value/sitegen/pages.py:162
영향렌즈 3개 카테고리 탭 — 제품 159개(48.0%)의 열람 경로
검증빌드 후 dist/assets/에 5개 파일만 존재. nikon-lens-lineup.jpg 없음 (git에는 추적됨)

홈 페이지는 assets/nikon-lens-lineup.jpg를 렌즈 카테고리 전용 히어로로 참조하고 (site.js:407-412의 updateHeroImage()가 z-mount-lenses·f-mount-lenses·classic-lenses 선택 시 표시), 이 파일은 저장소에 커밋되어 있습니다. 그러나 copy_assets()는 이 파일을 산출물에 복사하지 않습니다.

2.3 이전에는 무해했습니다. Pages가 저장소 루트를 직접 서빙했으므로 assets/가 그대로 노출됐기 때문입니다. artifact 배포로 전환하면서 "산출물에 포함된 것만 서빙된다"로 규칙이 바뀌었고, 이 파일만 이관 목록에서 빠졌습니다. 마이그레이션 회귀입니다.

테스트가 놓친 이유

test_artifact_is_self_contained_for_pages_deploy는 auth-complete.html·catalog.json·히스토리 JSON의 존재만 확인합니다. 골든 테스트는 생성된 HTML 문자열을 비교하므로, 문자열에 src="assets/nikon-lens-lineup.jpg"가 들어 있으면 통과합니다 — 그 경로에 파일이 실제로 있는지는 아무도 검사하지 않습니다. 

# nikon_value/sitegen/build.py — copy_assets()에 1줄 추가
shutil.copy2(PROJECT_ROOT / 'assets' / 'nikon-lens-lineup.jpg',
             output_dir / 'assets' / 'nikon-lens-lineup.jpg')

# tests/test_build_output.py — 재발 방지 테스트 (이 종류의 버그 전체를 차단)
def test_every_local_asset_reference_exists(site_dir):
    """생성된 모든 HTML의 로컬 src/href가 산출물에 실제로 존재해야 한다."""
    missing = []
    for html_path in [site_dir / 'index.html', site_dir / 'resources.html',
                      *(site_dir / 'products').glob('*.html')]:
        html = html_path.read_text(encoding='utf-8')
        for ref in re.findall(r'(?:src|href)="((?!https?:|//|#|mailto:)[^"]+)"', html):
            target = (html_path.parent / ref.split('?')[0]).resolve()
            if not target.exists():
                missing.append(f'{html_path.name} -> {ref}')
    assert not missing, f'산출물에 없는 참조: {sorted(set(missing))[:20]}'

5.2 P1 D-2 · eBay API 호출량이 일일 무료 한도에 도달

ebay.py의 적응형 가격 탐색은 검색 결과 최고가가 상한의 98% 이상이면 상한을 1.5배·2.0배로 올려 재검색합니다. 훌륭한 설계지만, 발견한 상한을 config/products.yaml에 되먹이지 않기 때문에 같은 확장이 매 실행마다 영구 반복됩니다.

구분제품 수회당 추가 검색
기본 검색 (전 제품)331331
매물 0건 → should_expand_max_price가 항상 True 반환3162
관측 최고가 ≥ 설정 상한의 98% → 확장 트리거103 (31.1%)206

가정: 확장 트리거 제품은 2단계 모두 실행, 페이지네이션(limit=200)은 미포함(최소 340페이지 추가 요인 존재). eBay Browse API 무료 한도는 애플리케이션당 일 5,000회입니다. 실제 호출 로그가 없으므로 정확한 소진율은 확인 불가이지만, ebay.py에 6단계 지수 백오프 429 핸들러가 이미 구현돼 있다는 사실 자체가 한도에 닿고 있다는 정황 증거입니다.

설정 상한이 실제 시장 천장보다 낮은 대표 사례: nikon-z7ii(상한 $2,500 / 관측 $3,567), nikkor-z-135mm-f18-s-plena($3,000 / $3,476), nikon-z7($1,800 / $2,288). 이 103개는 매 수집마다 잘린 가격 창으로 1차 검색을 낭비한 뒤 재검색하고 있으며, 그 결과는 다음 실행에 반영되지 않습니다.

5.3 P1 D-3 · 산출물에 7 MB 규모의 동일 데이터 이중 수록

제품 페이지 331장(11.1 MB) 중 7.0 MB(63%)가 <script id="history-data"> 인라인 JSON입니다. 그런데 완전히 같은 데이터가 dist/data/products/*.json(8.05 MB)로 한 번 더 실려 나갑니다 — 후자는 관심목록 대시보드가 fetch로 읽기 위해 2.3에서 추가된 것입니다.

사용자 대역폭 관점에서는 문제가 아닙니다(페이지당 gzip 7KB). 실제 비용은 artifact 업로드/다운로드 시간과 배포 지연이며, 데이터 갱신 때마다 23MB artifact가 매번 재생성·재업로드됩니다. 인라인을 제거하고 제품 페이지도 data/products/{id}.json을 fetch하도록 통일하면 산출물이 약 30% 줄고 데이터 표현이 한 곳으로 수렴합니다. 다만 <noscript> 히스토리 테이블(SEO·접근성)은 유지해야 하므로, 최근 10건만 인라인 + 전체는 fetch가 현실적 절충안입니다.

5.4 P1 D-4 · data/daily/가 data/products/와 100% 중복

최신 스냅샷(2026-07-28.json)의 331개 제품 전부에 대해 data/products/{id}.json의 같은 날짜 항목과 대조한 결과 불일치 0건, 누락 0건이었습니다. 두 저장소는 같은 통계를 축(제품 ↔ 날짜)만 바꿔 담고 있으며, daily/만 가진 고유 정보는 환율 1개 필드뿐입니다.

현재 8.3 MB, 보관 한도 400일이므로 최대 22 MB까지 증가합니다. git 객체 249,935개 중 data/ 관련이 140,722개(56.3%)이고 .git은 5개월 만에 136 MB에 도달했습니다. 

# 대안: daily 스냅샷을 환율 시계열로 축소 (제품 통계는 products/가 이미 보유)
# data/exchange-rates.json  ← 단일 파일, 날짜당 한 줄
[{"date": "2026-07-28", "rate": 1470.1115, "reference_date": "2026-07-27", "source": "ECB"}, ...]
# 효과: 8.3MB → 약 20KB, 커밋당 변경 파일 83개 → 약 60개
기존 데이터 처리 주의 daily/를 삭제해도 제품 통계는 손실되지 않지만(products/에 동일 내용 존재), _recover_exchange_rate_from_daily()가 이 디렉터리를 폴백 경로로 사용합니다(exchange.py:18-31). 스키마를 바꾸기 전에 이 폴백을 새 파일로 먼저 옮기고, 과거 환율은 기존 스냅샷에서 일괄 추출해 이관해야 합니다. git 히스토리를 재작성해 저장소를 줄이는 방식은 권장하지 않습니다 — 이득 대비 위험이 큽니다.

5.5 P1 D-5 · 가격 알림이 전면 비활성 상태로 사용자에게 노출됨

server/notify.py:19-22의 send_price_alert()는 항상 False를 반환합니다. 체커는 "발송 성공 시에만 triggered 갱신" 규칙을 따르므로 알림은 영원히 대기 상태로 누적되고, 매 시간 카탈로그 갱신마다 같은 행을 다시 평가합니다. 설계 의도(채널 연동 시 자동 발송)는 타당하지만, UI는 이미 목표가 입력 패널을 노출하고 있어 사용자는 알림이 동작한다고 믿게 됩니다.

auth.js:294·350-351에 "알림 채널(텔레그램·카카오톡)은 연동 준비 중입니다"라는 안내가 있어 완전한 오인은 아니지만, 6월 10일 SMTP 제거 이후 7주간 어떤 알림도 발송되지 않은 상태입니다. 기능 완결이 필요합니다(7장 F-2).

5.8 P2 D-8 · 리버스 프록시 뒤 rate limit 무력화 가능성

rate_limit.py는 slowapi.util.get_remote_address를 사용하며 이는 request.client.host를 읽습니다. 서버가 cantabile.tplinkdns.com 뒤에서 리버스 프록시(nginx 등)를 거친다면 모든 요청이 프록시 IP 하나로 집계되어 OAuth 5회/분 제한이 전체 사용자 공유 버킷이 됩니다(정상 사용자 차단) 또는 프록시 설정에 따라 무의미해집니다.

저장소에 프록시 설정이 없어 실제 배포 형태를 확인할 수 없습니다. uvicorn --proxy-headers --forwarded-allow-ips=<프록시IP> 사용 여부를 확인하고, 배포 문서(D-7)에 명시하십시오.

  • 커버리지 게이트: CI에 --cov-fail-under=75를 넣어 회귀 방지 (현재 60%이므로 Phase 2 완료 후 적용)

7.추가 기능 제안

기존 데이터 자산(331제품 × 최대 365일 시계열)에서 도출 가능하고, 구현 비용 대비 효용이 높은 순서로 정리했습니다.

F-1 · eBay 어필리에이트 수익화 즉시 · 코드 변경 거의 없음

ebay.py:64-66에 EPN 캠페인 컨텍스트 전송 코드가 이미 있습니다. 그런데 update-prices.yml은 EBAY_EPN_CAMPAIGN_ID를 전달하지 않습니다 — 즉 어필리에이트 링크가 한 번도 생성된 적이 없습니다. 사이트는 이미 딜 레이더 617건 + 제품당 샘플 매물 5건으로 eBay 아웃바운드 링크를 대량 노출하고 있으므로, EPN 가입 후 시크릿 1개를 워크플로에 추가하는 것만으로 수익 경로가 열립니다. 

# .github/workflows/update-prices.yml
        env:
          EBAY_CLIENT_ID: ${{ secrets.EBAY_CLIENT_ID }}
          EBAY_CLIENT_SECRET: ${{ secrets.EBAY_CLIENT_SECRET }}
          OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
          EBAY_EPN_CAMPAIGN_ID: ${{ secrets.EBAY_EPN_CAMPAIGN_ID }}   # 추가

주의: 어필리에이트 링크 사용 시 사이트에 제휴 관계 고지가 필요합니다(FTC·공정위 기준). build_footer()에 한 줄 추가하십시오. 현재 rel="nofollow"가 붙어 있는데, EPN 링크는 추적 파라미터가 유효해야 하므로 링크 생성 방식 확인이 필요합니다.

F-2 · 텔레그램 알림 채널 기능 완결

D-5의 해소책입니다. 상태 머신(도달 → 발송 → 회복 시 재무장)과 API·UI가 모두 완성돼 있고 send_price_alert() 구현 하나만 비어 있습니다. 텔레그램 봇이 최소 경로입니다:

  • DB에 users.telegram_chat_id 컬럼 추가 (nullable)
  • /api/me/telegram으로 연동 코드 발급 → 사용자가 봇에 코드 전송 → 서버가 chat_id 저장
  • send_price_alert()가 sendMessage 호출 후 성공 여부 반환

카카오톡은 "나에게 보내기" 외에는 비즈니스 채널 심사가 필요하므로 텔레그램을 먼저 붙이는 편이 현실적입니다. 대기 중인 알림은 채널 연동 즉시 다음 점검 주기에 자동 발송됩니다 — 기존 설계가 이미 그렇게 되어 있습니다.

F-3 · 실거래가(Sold) 데이터 도입 정확도 근본 개선

현재 모든 수치는 호가(asking price)입니다. 사이트 곳곳에 "실제 거래가와 다를 수 있습니다"라는 고지가 있고 이는 정직한 처리이지만, 중고 시세 트래커의 본질적 가치는 실거래가에 있습니다. eBay Marketplace Insights API는 최근 90일 낙찰가를 제공하지만 파트너 승인이 필요합니다. 승인이 어렵다면 차선책으로 매물 소멸 추적이 가능합니다 — 수집 때마다 아이템 ID를 기록해 두고, 다음 수집에서 사라진 매물을 "판매 추정"으로 분류하면 호가 대비 실제 성사 가격대를 통계적으로 근사할 수 있습니다. 이미 3시간 간격 수집 인프라가 있으므로 추가 API 비용이 없습니다.

F-4 · 모델 비교 뷰

"Z6 III vs Z8 vs Z9를 한 차트에서" 같은 요구는 이 카테고리 사이트의 최다 유입 질의입니다. 데이터(data/products/*.json)와 차트 코드가 이미 있으므로 compare.html?ids=a,b,c 페이지 하나로 구현됩니다. 관심목록 대시보드의 fetchHistory·Chart.js 온디맨드 로딩 로직을 그대로 재사용할 수 있습니다.

F-5 · 감가 곡선과 "구매 적기" 신호

누적 5개월(약 150일) 시계열이 쌓였습니다. 제품별 출시 연차 대비 가격 하락률을 회귀하면 "이 렌즈는 연 8% 감가, 현재 추세선 대비 12% 저평가" 같은 판단 근거를 제시할 수 있습니다. 이미 compute_price_change(30일)와 "1년 내 최저" 뱃지가 있으므로 자연스러운 확장입니다. 단, 투자 조언으로 읽히지 않도록 문구 설계에 주의가 필요합니다.

F-6 · 관심목록 → 컬렉션 포트폴리오

현재 관심목록 대시보드는 중앙값 합산과 추이만 보여줍니다. 여기에 구매가·구매일 입력을 추가하면 "내 장비 총 시세 $12,400 / 취득가 대비 −8%" 같은 개인화 지표가 됩니다. 카메라 수집가는 이 숫자를 보려고 재방문하므로 리텐션 효과가 큽니다. DB 스키마 확장은 favorites 테이블에 purchase_price·purchase_date 컬럼 추가로 끝납니다.

F-7 · 유동성 지표 (희소성의 정량화)

count(현재 매물 수) 시계열은 이미 저장되고 있지만 어디에도 표시되지 않습니다. "평균 매물 3건 · 최근 90일 중 21일은 0건" 같은 지표는 희귀 모델 구매자에게 가격만큼 중요한 정보이며, 현재 is_rare가 수동 설정값(products.yaml)인 것을 데이터 기반으로 자동 판정하는 근거도 됩니다. 추가 수집 없이 기존 데이터만으로 구현됩니다.

F-8 · 딜 레이더 RSS/JSON 피드

빌드 시 deals.json·deals.xml을 함께 생성하면 재방문 없이도 사용자가 딜을 받아볼 수 있습니다. 정적 파일 2개 추가로 끝나며, D-10(딜 링크 신선도)의 완화책도 됩니다 — 피드에는 수집 시각을 명시하면 됩니다.

F-9 · 영문 페이지

데이터 출처가 eBay 미국이고 니콘 클래식 렌즈 수요는 영어권이 훨씬 큽니다. name_en·rarity_*가 이미 구조화돼 있고 페이지 빌더가 함수로 분리돼 있으므로, 문자열 테이블 분리 + /en/ 경로 생성으로 대응 가능합니다. sitemap·hreflang 처리 포함. 다만 331 × 2 = 662 페이지가 되므로 D-3(산출물 중복) 해소를 선행하는 편이 좋습니다.

우선순위 제안 F-1(수익화)과 F-2(알림 완결)은 이미 90% 만들어진 것을 마무리하는 작업이므로 가장 먼저 하십시오. 그다음은 기존 데이터만으로 새 가치를 만드는 F-7 → F-4 → F-6 순을 권합니다. F-3(실거래가)은 이 제품의 정확도 상한을 결정하는 가장 근본적인 개선이지만 외부 승인 의존성이 있으므로 별도 트랙으로 진행하십시오.

8.유지해야 할 자산

리팩토링 과정에서 훼손하기 쉬운, 그러나 이 프로젝트의 실질적 경쟁력인 요소들입니다.

  • 3중 필터 파이프라인의 폴백 규율 — 규칙 필터가 전부를 걸러내면 원본 유지(filters.py:175-177), LLM이 전부를 걸러내면 규칙 결과 유지(llm.py:176-181), LLM 예외 시에도 규칙 결과 유지(llm.py:185-187). "자동 필터는 틀릴 수 있으므로 데이터를 지우지 않는다"는 원칙이 세 곳에 일관되게 구현돼 있습니다. 캐시(Phase 1)를 도입할 때 이 폴백 의미를 반드시 보존하십시오.
  • 환율 3단계 폴백 — ECB 실패 → 기존 catalog 값 유지 → 최근 daily 스냅샷 복구. D-4 개편 시 이 3단계를 그대로 옮겨야 합니다.
  • 알림 상태 머신의 "발송 성공 시에만 소비" 규칙 — 채널 장애 시 알림이 소실되지 않고 자동 재시도되는 근거입니다. F-2 구현 시 반드시 유지.
  • 골든 파일 테스트 — 7종 산출물을 바이트 단위로 고정. Jinja2 마이그레이션 같은 대규모 변경의 유일한 안전망입니다. UPDATE_GOLDENS=1 재생성 절차가 문서화된 것도 좋습니다.
  • API 서버 없이도 동작하는 정적 사이트 — auth.js의 apiFetch가 네트워크 실패를 삼키고 null을 반환해 시세 조회는 계속 동작합니다(auth.js:52-55). 라즈베리파이 다운타임이 사이트 전체 장애로 번지지 않는 구조입니다.
  • admin 서버 3중 방어 — local-only + same-origin + 세션 토큰. 로컬 도구에 대한 적정 수준입니다.
  • 수집 실패 시 GitHub 이슈 자동 생성 + 2일 이상 stale 시 사이트 배너 — 개인 프로젝트로서는 드문 수준의 운영 가시성입니다.
과잉 리팩토링 경계 build_home_page·build_product_page의 CC 30/28은 수치상 나쁘지만 커버리지 97% + 골든 테스트로 보호되고 있어 실제 위험은 낮습니다. Jinja2 도입은 "복잡도 수치를 낮추기 위해서"가 아니라 F-9(영문 페이지)처럼 템플릿 변형이 실제로 필요해질 때 착수하십시오. 반면 fetch.main()의 CC 26은 커버리지 17%와 겹치므로 실제 위험이며 Phase 2 대상입니다. 같은 복잡도라도 안전망 유무에 따라 우선순위가 달라집니다.
